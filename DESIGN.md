# DESIGN — auditgym

Проектная записка. Разделы — по ТЗ (`docs/TZ.md`). Версии компонентов не
дублируются здесь числами: они заданы константами `auditgym.ENV_VERSION`,
`auditgym.generator.GENERATOR_VERSION`, `auditgym.generator.CONFIG_VERSION`,
`auditgym.grader.GRADER_VERSION` и записываются в каждую строку `results.csv`.

## 1. Устройство среды

См. [`docs/env.md`](docs/env.md): `AuditEnv(mode="train"|"eval").reset(seed, config) -> (obs, info)`, `.step(action) -> (obs, reward, terminated, truncated, info)`; 5 действий (`list_records`, `get_record`, `get_document`, `calculator`, `submit`), 100 шагов и 60 с на эпизод, каждое действие стоит 1 шаг, ограниченные ошибки без подсказок.
## 2. Генерация: скрытая история → документы → ошибки

См. [`docs/generator.md`](docs/generator.md#конвейер): история → чистый рендер + строгие инварианты → инъекция с записью причинных изменений → рендер → независимая проверка эталонным аудитором и достаточностью доказательств.
## 3. Канонические affected_ids и наборы доказательств по типам ошибок

См. [`docs/generator.md`](docs/generator.md#канонический-эталон-truthjson) — таблица правил по 4 типам и сценарии A/B.
## 4. Нормализация, допуски, tie-break в matcher

Полностью — [`docs/grader.md`](docs/grader.md); код — `auditgym/grader/`. Кратко:

* **Нормализация ID** (`normalize.py`): trim; префикс таблицы → нижний регистр; валюты в `fx:<date>/<src>/<tgt>` → верхний регистр; `invoices:<doc_id>` / `payments:<doc_id>` — алиас ключа своей таблицы; дедупликация и сортировка. Сам ID не исправляется. ID без префикса (`INV-…`, `PAY-…`, `DOC-…`, row_id, ключ курса) приводится к каноническому виду, только если в публичных записях эпизода ровно одна запись с таким ключом; неизвестный или неоднозначный ID не сопоставляется, а вывод с ним — FP. Валюта формата ISO, которой нет в эпизоде, и лишние поля внутри вывода не обнуляют ответ: такой вывод просто FP (grader 1.1.0).
* **Совместимость пары**: все ID существуют → тип → множество `affected_ids` = каноническому → валюта → |claimed − expected| ≤ 1 → хотя бы один `evidence_set` ⊆ `evidence_ids`. `explanation` не читается.
* **Допуск** `TOLERANCE_MINOR = max(1, единица округления policy) = 1` минимальная единица, одинаков для всех типов, константа в `auditgym/grader/constants.py`; поле `tolerance_minor` из `truth.json` не используется.
* **Сопоставление**: максимальное паросочетание (min-cost max-flow), среди максимальных — наименьший ключ `(Σ|разница сумм|, Σ позиций выводов, Σ рангов issue по issue_id)`. TP не зависит от порядка выводов; tie-break решает только, какой из равных выводов получит зачёт. Повторы и несопоставленные выводы — FP, несопоставленные issue — FN.

## 5. Награда и метрики

* `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, `F1 = 2TP/(2TP+FP+FN)`; нулевой знаменатель → 0; пустой эталон и пустой ответ → F1 = 1; пустой эталон и есть выводы → F1 = 0.
* `reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, `inspection_steps` = шаги до `submit` без самого `submit` (при обрыве — все шаги, ответ = `findings: []`). Неверная структура → −1. Одна общая награда, экспериментальной нет.
* Арифметика точная (`Fraction`), результат детерминирован побитово. Агент получает только `reward` и только в `train`; диагностика (`matches`, `finding_reasons`, `missed_issue_ids`, `by_type`) — только в `env.grade_log`.
* Надёжность — 20 проверок R01–R20 в `tests/grader/test_grader_reward_checks.py` (таблица в `docs/grader.md`); `python -m auditgym.grader selfcheck` — oracle = 1.0, молчание, flag-all < 0, перестановка и смена ID на каждом эпизоде.
## 6. Изоляция и защита от утечек

См. [`docs/env.md`](docs/env.md#изоляция-и-защита-от-утечек): среда хранит только публичную часть эпизода; в `eval` эпизод генерируется и оценивается в отдельном процессе, откуда в среду приходят только публичные записи и оценка; данные отдаются копиями; leak-scan проверяет наблюдения, `info` и траектории.
## 7. Измеренный разбор сбоев базовых политик

Политики работают через API `AuditEnv` и настоящий `Grader`. Публичная страница
разбирается из `result.items[*].record`; итоговая оценка читается из нового элемента
`env.grade_log`, без повторного вызова score. В операторский CSV передаются только
скалярные метрики и версии; matches, finding_reasons, missed_issue_ids и ошибки
оценщика в траектории не копируются.

### 7.1. Четыре базовые политики

`make artifacts` (файлы в `artifacts/`): 20 эпизодов train + dev, режим train,
RandomExplorer с seed 7 (значение CLI по умолчанию). P, R, F1, reward, return, шаги
и время — средние по эпизодам; P/R micro — по суммам TP/FP/FN. Время — один прогон
на ноутбуке (Apple Silicon, Python 3.12), для ориентира.

| Политика | P | R | F1 | reward | return | шаги | время, с | P micro | R micro | выводов |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Oracle | 0.750 | 0.750 | 1.000 | 1.000 | 1.000 | 1.0 | 0.005 | 1.000 | 1.000 | 95 |
| Reconciler | 0.750 | 0.750 | 1.000 | 0.960 | 0.960 | 21.1 | 0.055 | 1.000 | 1.000 | 95 |
| RandomExplorer (seed 7) | 0.000 | 0.000 | 0.250 | −0.504 | −0.504 | 9.0 | 0.011 | — | 0.000 | 0 |
| FlagAll | 0.000 | 0.000 | 0.000 | −1.000 | −1.000 | 2.0 | 0.010 | 0.000 | 0.000 | 600 |

Как читать:

* В 5 из 20 эпизодов ошибок нет. Грейдер ставит там P = R = 0 (нулевой знаменатель)
  и F1 = 1 за пустой ответ, поэтому средние P и R даже у Oracle равны 0,75.
  Колонки micro этого искажения не имеют.
* return = reward: награда выдаётся только на последнем шаге.
* FlagAll выдвигает 30 обвинений на эпизод (по 4 типа на первые документы) с суммой 0
  и без нужных доказательств: ни одно не совпадает с эталоном, reward = −1.
* RandomExplorer с seed 7 тратит 8 шагов на случайный просмотр и сдаёт пустой ответ
  во всех 20 эпизодах: F1 = 1 на 5 чистых эпизодах, иначе 0. С seed 42 (демо) он
  каждый раз делает один случайный вывод и получает F1 = 0, reward = −1 везде.
* Reconciler читает все четыре таблицы постранично (10–45 шагов) и сверяет их.
  **Он закодирован по тем же правилам, что эталонный аудитор генератора
  (`auditgym/generator/audit.py`)**: те же признаки дубликата, то же правило
  распределения оплаты, тот же выбор курса и та же граница периода. Поэтому его
  F1 = 1 — верхняя граница для скриптового эксперта, знающего правила, а не
  доказательство того, что задача тривиальна для обучаемого агента. Правила при этом
  открыты агенту: они записаны текстом в `policy.json` эпизода.

### 7.2. Абляции: сколько стоит каждая ловушка

Чтобы измерить, работают ли отвлекающие случаи и варианты ошибок, у Reconciler по
одному убираются знания, которые он использует (`auditgym/policies/ablations.py`,
существующие политики не меняются; без флагов вариант даёт ровно ответ Reconciler —
это проверяет `tests/policies/test_ablations.py`). Каждый вариант проходит через
настоящие `AuditEnv` (train) и `Grader` на тех же 20 эпизодах.

| Вариант | что убрано |
|---|---|
| `no_tz_period` | граница периода по календарной дате UTC, а не по времени в часовом поясе компании |
| `no_tz_fx_date` | дата курса — дата документа по UTC, а не местная |
| `no_weekend_fx_rule` | нет правила «последний курс на дату или раньше»: в день без курса (выходной) берётся следующий опубликованный |
| `loose_duplicates` | дубликат = тот же клиент, валюта и сумма; строки счёта не сравниваются |
| `flag_partial` | любая оплата, после которой счёт остаётся частично открытым, считается ошибкой распределения (в дополнение к обычному правилу) |
| `all_ablations` | все пять сразу |

Воспроизвести: `make failure-analysis` или
`python tools/failure_analysis.py --json artifacts/failure_analysis.json`
(около 10 с; результат в `artifacts/failure_analysis.md`).

P, R — micro по суммам; F1, reward — средние по эпизодам; TP/FP/FN — суммы
(всего 95 ошибок в эталоне).

| Вариант | P | R | F1 | reward | TP | FP | FN | FP по типам | FN по типам |
|---|---:|---:|---:|---:|---:|---:|---:|---|---|
| Reconciler (полный) | 1.000 | 1.000 | 1.000 | 0.960 | 95 | 0 | 0 | — | — |
| no_tz_period | 0.800 | 0.884 | 0.747 | 0.460 | 84 | 21 | 11 | cutoff 21 | cutoff 11 |
| no_tz_fx_date | 0.544 | 0.916 | 0.631 | 0.228 | 87 | 73 | 8 | fx 73 | fx 8 |
| no_weekend_fx_rule | 0.340 | 0.863 | 0.423 | −0.185 | 82 | 159 | 13 | fx 159 | fx 13 |
| loose_duplicates | 0.586 | 1.000 | 0.596 | 0.160 | 95 | 67 | 0 | dup 67 | — |
| flag_partial | 0.748 | 1.000 | 0.654 | 0.276 | 95 | 32 | 0 | alloc 32 | — |
| all_ablations | 0.167 | 0.684 | 0.237 | −0.557 | 65 | 324 | 30 | dup 67, alloc 30, fx 208, cutoff 19 | fx 18, cutoff 12 |

Причины FP — первая не пройденная проверка matcher для ближайшей ошибки
(`finding_reasons` из `grade_log`): `affected_ids` — документ выбран неверно,
`amount` — документ верный, сумма нет, `type` — нет ошибки такого типа рядом,
`no_issues` — в эпизоде ошибок нет вообще. Источник FP определяется после оценки по
`private/provenance.json` (поле `distractors`); «не отвлекающий» — обычный документ,
который генератор не помечал как ловушку.

| Вариант | причины FP | источник FP |
|---|---|---|
| no_tz_period | affected_ids 14, no_issues 7 | boundary 11, recurring 3, не отвлекающий 7 |
| no_tz_fx_date | affected_ids 62, amount 5, no_issues 6 | не отвлекающий 55, recurring 6, boundary 4, partial_payment 4, split_payment 3, refund 1 |
| no_weekend_fx_rule | affected_ids 121, amount 4, no_issues 34 | не отвлекающий 95, weekend_fx 22, recurring 14, split_payment 12, partial_payment 5, prior_invoice 5, boundary 4, refund 2 |
| loose_duplicates | affected_ids 42, no_issues 22, type 3 | recurring 67 |
| flag_partial | affected_ids 20, no_issues 8, type 4 | partial_payment 32 |
| all_ablations | affected_ids 233, no_issues 76, amount 8, type 7 | не отвлекающий 138, recurring 89, partial_payment 37, weekend_fx 22, boundary 17, split_payment 13, prior_invoice 5, refund 3 |

Выводы:

* Каждое отдельное упрощение снижает средний F1 до 0,42–0,75, а reward — с 0,96 до
  −0,19…0,46. Все вместе — F1 0,24, reward −0,56; пустой ответ на всех 20 эпизодах
  дал бы reward −0,5 (как RandomExplorer с seed 7).
* Отвлекающие случаи срабатывают ровно на свою ловушку: `recurring` (одинаковая
  сумма и клиент, разные строки) даёт все 67 FP у `loose_duplicates`;
  `partial_payment` — все 32 FP у `flag_partial`; `boundary` (документы у края
  периода в UTC) — 11 из 21 FP у `no_tz_period`.
* Ошибки курса и периода опасны не только из-за отвлекающих случаев: документы на
  выходных и около полуночи встречаются и в обычном потоке, поэтому большинство FP
  у FX-абляций приходится на «не отвлекающие» документы. Кроме того, такие
  абляции пропускают настоящие ошибки (FN 8–13): например, вариант ошибки FX
  `utc_date` в генераторе как раз совпадает с расчётом по дате UTC.
* Ограничение анализа: абляции — ручные гипотезы о типичных ошибках агента, а не
  поведение обученной модели; они показывают, что ловушки различимы и штрафуются,
  но не оценивают, насколько легко их выучить.

Приёмка — 20 selfcheck-эпизодов × 4 политики × 4 критерия (320 проверок).
Дополнительно проверяются все политики в train/eval, схема trajectory_line,
получение записей RandomExplorer, нулевое число шагов при тайм-ауте до действия
и отсутствие приватной диагностики в журнале агента.

## 8. Честные ограничения

* Все данные синтетические; обучение весов не проводилось, проверялись только
  скриптовые политики. Качество на этих эпизодах не доказывает применимость к
  реальному аудиту.
* Reconciler повторяет правила эталонного аудитора генератора, поэтому F1 = 1 у него —
  потолок, а не оценка сложности (см. §7.2).
* Selfcheck-эпизоды открыты. API не является песочницей для произвольного
  недоверенного Python-кода. Проверка утечек объединяет контракт среды и проверки
  runner, но не доказывает отсутствие любых скрытых каналов.
* Python-зависимости закреплены точно (`requirements.lock`), но без хешей; базовый
  Docker-образ `python:3.11-slim` закреплён тегом, без digest.
* Веб-интерфейс (`ui/`) подключён к настоящему API команды (эпизоды, генерация,
  AuditEnv, runner, grader), но это только просмотрщик: он не участвует в
  `make check` как часть оценки среды и на метрики не влияет. Его HTTP-тесты входят в
  `make check`, браузерные — в отдельный CI-job.
* Локальные замеры сделаны на macOS / Python 3.12; Linux / Python 3.11 и ограничения
  Docker (без сети, 2 CPU, 4 GiB) проверяет CI-job `isolated-container`.
