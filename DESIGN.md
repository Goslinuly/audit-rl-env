# DESIGN — auditgym

> Заполняется командой к 21.11. Разделы — по ТЗ (`docs/TZ.md`).

## 1. Устройство среды

См. [`docs/env.md`](docs/env.md): `AuditEnv(mode="train"|"eval").reset(seed, config) -> (obs, info)`, `.step(action) -> (obs, reward, terminated, truncated, info)`; 5 действий (`list_records`, `get_record`, `get_document`, `calculator`, `submit`), 100 шагов и 60 с на эпизод, каждое действие стоит 1 шаг, ограниченные ошибки без подсказок.
## 2. Генерация: скрытая история → документы → ошибки

См. [`docs/generator.md`](docs/generator.md#конвейер): история → чистый рендер + строгие инварианты → инъекция с записью причинных изменений → рендер → независимая проверка эталонным аудитором и достаточностью доказательств.
## 3. Канонические affected_ids и наборы доказательств по типам ошибок

См. [`docs/generator.md`](docs/generator.md#канонический-эталон-truthjson) — таблица правил по 4 типам и сценарии A/B.
## 4. Нормализация, допуски, tie-break в matcher

Полностью — [`docs/grader.md`](docs/grader.md); код — `auditgym/grader/`. Кратко:

* **Нормализация ID** (`normalize.py`): trim; префикс таблицы → нижний регистр; валюты в `fx:<date>/<src>/<tgt>` → верхний регистр; `invoices:<doc_id>` / `payments:<doc_id>` — алиас ключа своей таблицы; дедупликация и сортировка. Сам ID не исправляется, таблица не подбирается; ID без префикса или отсутствующий в публичных записях не сопоставляется, а вывод с таким ID — FP.
* **Совместимость пары**: все ID существуют → тип → множество `affected_ids` = каноническому → валюта → |claimed − expected| ≤ 1 → хотя бы один `evidence_set` ⊆ `evidence_ids`. `explanation` не читается.
* **Допуск** `TOLERANCE_MINOR = max(1, единица округления policy) = 1` минимальная единица, одинаков для всех типов, константа в `auditgym/grader/constants.py`; поле `tolerance_minor` из `truth.json` не используется.
* **Сопоставление**: максимальное паросочетание (min-cost max-flow), среди максимальных — наименьший ключ `(Σ|разница сумм|, Σ позиций выводов, Σ рангов issue по issue_id)`. TP не зависит от порядка выводов; tie-break решает только, какой из равных выводов получит зачёт. Повторы и несопоставленные выводы — FP, несопоставленные issue — FN.

## 5. Награда и метрики

* `P = TP/(TP+FP)`, `R = TP/(TP+FN)`, `F1 = 2TP/(2TP+FP+FN)`; нулевой знаменатель → 0; пустой эталон и пустой ответ → F1 = 1; пустой эталон и есть выводы → F1 = 0.
* `reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)`, `inspection_steps` = шаги до `submit` без самого `submit` (при обрыве — все шаги, ответ = `findings: []`). Неверная структура → −1. Одна общая награда, экспериментальной нет.
* Арифметика точная (`Fraction`), результат детерминирован побитово. Агент получает только `reward` и только в `train`; диагностика (`matches`, `finding_reasons`, `missed_issue_ids`, `by_type`) — только в `env.grade_log`.
* Надёжность — 20 проверок R01–R20 в `tests/grader/test_grader_reward_checks.py` (таблица в `docs/grader.md`); `python -m auditgym.grader selfcheck` — oracle = 1.0, молчание, flag-all < 0, перестановка и смена ID на каждом эпизоде.
## 6. Изоляция и защита от утечек

См. [`docs/env.md`](docs/env.md#изоляция-и-защита-от-утечек): среда хранит только публичную часть эпизода; в `eval` эпизод генерируется и оценивается в отдельном процессе, откуда в среду приходят только публичные записи и оценка; данные отдаются копиями; leak-scan проверяет наблюдения, `info` и траектории.
## 7. Измеренный разбор сбоев базовых политик

Политики и runner участника 4 работают через API среды участника 2 и grader
участника 3. Публичная страница разбирается из `result.items[*].record`; итоговая
оценка читается из нового элемента `grade_log`, без повторного вызова score.
В операторский CSV передаются только скалярные метрики и версии; matches,
finding_reasons, missed_issue_ids и ошибки оценщика в траектории не копируются.

Измерено на 21 опубликованном эпизоде, RandomExplorer seed=42: Oracle и Reconciler
имеют средний F1=1; FlagAll и RandomExplorer — F1=0. Максимум шагов — 1, 45, 2 и 9
соответственно. FlagAll делает безусловные обвинения без достаточных доказательств;
RandomExplorer просматривает малую случайную часть данных и делает случайный
вывод. Reconciler реализует открытые синтетические правила, а не обученную модель.

Приёмка — 20 selfcheck-эпизодов × 4 политики × 4 критерия (320 проверок).
Дополнительно проверяются все политики в train/eval, схема trajectory_line,
получение записей RandomExplorer, нулевое число шагов при тайм-ауте до действия
и отсутствие приватной диагностики в журнале агента.

Качество на этих эпизодах не доказывает применимость к реальному аудиту.

но не доказывает отсутствие любых скрытых каналов. Прототип UI пока работает
с демонстрационными данными. Локальные результаты относятся к Windows/Python 3.12;
Linux/Python 3.11 и ограничения Docker подтверждаются отдельным CI-job.
