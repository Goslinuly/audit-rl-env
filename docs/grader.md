# Оценщик (`auditgym.grader`)

Владелец: участник 3. Контракт для среды (участник 2), runner и политик (участник 4) и жюри: как устроены валидация, нормализация, сопоставление и награда. Всё ниже — открытый код, правила не меняются без смены `GRADER_VERSION`.

## Быстрый старт

```python
from auditgym.grader import Grader
res = Grader().score(findings, truth=truth, public=public, inspection_steps=12)  # так вызывает среда
res = Grader().score(findings, "episodes/dev/dev_03", inspection_steps=12)       # прямо с диска
res.reward, res.precision, res.recall, res.f1, res.tp, res.fp, res.fn
res.matches          # [{finding_index, issue_id, amount_diff}]
res.finding_reasons  # по каждому выводу: "tp" или причина отказа (см. ниже)
res.missed_issue_ids, res.by_type, res.errors, res.valid, res.grader_version
```

```bash
python -m auditgym.grader score --episode episodes/dev/dev_07 --findings answer.json --steps 20
python -m auditgym.grader selfcheck            # oracle = 1, молчание, flag-all < 0, перестановка, смена ID на всех эпизодах
```

Среда подхватывает оценщик автоматически (`auditgym.env.grading.default_grader`): заглушка `StubGrader` больше не используется. Агент получает только `reward` и только в режиме `train`; всё остальное уходит в `env.grade_log` (для runner и разбора сбоев).

Оценщик — чистая функция: без случайности, часов и глобального состояния, входные данные не изменяет (проверяется тестом R20). Арифметика награды точная (`Fraction`), в `float` переводится один раз — одинаковые входы дают побитово одинаковую награду.

## 1. Валидация `findings.json` (`validate.py`)

Любое нарушение → вся отправка недействительна, `reward = −1`, `valid = false`, текст ошибок — в `errors` (в журнал оценщика, не агенту).

Принцип (с версии **1.1.0**): −1 за весь ответ — только за нарушение *структуры*. Если отдельный вывод хорошо сформирован, но неверен по содержанию (валюта не из эпизода, неизвестный ID), он просто не сопоставится и станет FP — остальные выводы ответа засчитываются.

| Поле | Правило |
| --- | --- |
| верхний уровень | объект: `episode_id` (строка, равна id эпизода), `findings` (список), необязательный `schema_version`; других ключей нет (строго) |
| `findings` | не больше **30** |
| вывод | объект с полями ниже; `explanation` необязателен; **неизвестные ключи внутри вывода** (например, `confidence`) игнорируются — не читаются и не являются ошибкой |
| `type` | одна из 4 строк точно: `duplicate_invoice`, `payment_allocation`, `fx_conversion`, `period_cutoff` |
| `affected_ids` | 1–10 непустых строк ≤ 128 символов |
| `evidence_ids` | 0–**10** непустых строк ≤ 128 символов |
| `claimed_amount_minor` | целое; `bool` и любой `float` (даже `100.0`) отвергаются; \|x\| ≤ 10¹⁸ |
| `currency` | строка; после trim + upper — три латинские буквы (формат ISO-4217). Не строка или не три буквы (`840`, `"US"`, `"dollars"`) → −1. Корректный код, которого нет в `manifest.currencies` (например, `CHF`), — **не ошибка структуры**: вывод валиден, но не сопоставится (FP, причина `currency`) |
| `explanation` | строка ≤ **1000** символов; оценщик её не читает |

Схема — `schemas/findings.schema.json` (у объекта вывода `additionalProperties: true`, у верхнего уровня — `false`); тест проверяет, что схема и валидатор принимают и отвергают одно и то же. Единственное различие: JSON Schema 2020-12 считает `100.0` целым, валидатор — нет.

Почему лишние ключи внутри вывода разрешены, а на верхнем уровне — нет: лишнее поле в выводе (`confidence`, `severity`) — частая и безвредная привычка LLM-агентов; оценщик читает только известные поля, поэтому такое поле не может ни помочь, ни навредить, а наказывать за него −1 за весь ответ несоразмерно. Верхний уровень остаётся строгим: обязательны `episode_id` и `findings`, а посторонний ключ вроде `reward` там — признак неверного формата ответа.

## 2. Нормализация (`normalize.py`)

Применяется к каждой строке `affected_ids` и `evidence_ids`:

1. trim;
2. разбить по первому `:` на `<table>` и `<id>`, trim обеих частей, `<table>` → нижний регистр;
3. `fx:<date>/<src>/<tgt>` — коды валют → верхний регистр;
4. алиас документа: `invoices:<doc_id>` → `invoices:<invoice_id>`, `payments:<doc_id>` → `payments:<payment_id>` — только если этот `doc_id` принадлежит документу этой таблицы;
5. **ID без префикса** (с 1.1.0): `INV-…`, `PAY-…`, `DOC-…`, `row_id` строки журнала, `<date>/<src>/<tgt>` курса → канонический `<table>:<id>`, **только если ровно одна публичная запись эпизода** имеет такой ключ (`DOC-…` → invoice/payment, которому принадлежит документ). Несуществующий или неоднозначный (есть в двух таблицах) ID без префикса остаётся как есть и не сопоставится никогда. Без публичных данных (`public=None`) ID без префикса не разрешаются;
6. дедупликация и сортировка.

Сам ID чувствителен к регистру и не исправляется: без нечёткого поиска, без подбора по части ID. Разрешение ID без префикса — точный поиск *существующего* ключа, поэтому угадывание не помогает: выдуманный ID остаётся неизвестным. ID, которого нет в публичных записях эпизода, — «неизвестный»; вывод с хотя бы одним неизвестным ID (в affected или evidence) не может быть TP. Валюта — trim + upper.

Неизвестные ключи вывода отбрасываются на этом же шаге (`matcher.normalize_finding` читает только известные поля).

## 3. Сопоставление (`matcher.py`)

Пара (вывод, issue) **совместима**, если по порядку:

| # | Проверка | Причина при отказе |
| --- | --- | --- |
| 1 | все ID вывода существуют в публичных записях | `unknown_id` |
| 2 | тот же `type` | `type` |
| 3 | множество `affected_ids` = каноническим `affected_ids` issue | `affected_ids` |
| 4 | та же валюта | `currency` |
| 5 | \|claimed − expected\| ≤ `TOLERANCE_MINOR` = **1** минимальная единица | `amount` |
| 6 | хотя бы один `evidence_set` issue ⊆ `evidence_ids` | `evidence` |

**Допуск** — константа оценщика: `max(1, единица округления policy)`, а policy округляет каждую строку до 1 минимальной единицы базовой валюты → 1 для всех типов. Поле `tolerance_minor` в `truth.json` оценщиком не используется.

**Паросочетание.** На двудольном графе совместимых пар берётся **максимальное** паросочетание (TP не зависит от порядка выводов и не бывает меньше возможного), а среди всех максимальных — с лексикографически наименьшим ключом
`(Σ|claimed − expected|, Σ позиций выводов в списке, Σ рангов issue по issue_id)`.
Это min-cost max-flow, решается точно последовательными кратчайшими путями (Беллман–Форд), выводов ≤ 30. Tie-break решает только *какой* вывод получит зачёт, но не *сколько*.

Вне паросочетания: каждый вывод — **FP** (включая точные повторы засчитанного вывода — причина `duplicate`), каждый issue — **FN**. В `finding_reasons` для FP указана первая не пройденная проверка относительно «ближайшего» issue (того, где пройдено больше проверок).

## 4. Метрики и награда (`reward.py`)

```
P  = TP / (TP + FP)            0 при нулевом знаменателе
R  = TP / (TP + FN)            0 при нулевом знаменателе
F1 = 2TP / (2TP + FP + FN)     пустой эталон и пустой ответ → 1; пустой эталон и есть выводы → 0
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)
```

`inspection_steps` — число шагов до `submit`, без самого `submit` (при обрыве по лимиту — все сделанные шаги; ответ при обрыве = `findings: []`). Экспериментальной награды нет: в результате одна общая `reward`.

Справочные значения:

| Ситуация | reward |
| --- | --- |
| полный верный ответ, 0 шагов | 1.0 |
| полный верный ответ за 10 / 90 шагов | 0.98 / 0.82 (разница ровно 0.16) |
| молчание на книге с ошибками | −1.0 |
| молчание на чистой компании, 0 / 100 шагов | 1.0 / 0.8 |
| любое обвинение на чистой компании | −1.0 |
| неверная структура | −1.0 |

Мутационная проверка самих тестов: каждая из подмен — широкий допуск, отключение проверки доказательств / валюты / неизвестных ID, «подмножество affected достаточно», дедупликация повторов, F1 = 1 на чистых при FP, приём float, снятие лимита 30, жадное сопоставление вместо максимального — роняет от 1 до 18 тестов.

## Ограничения

* Оценщик проверяет поля и доказательства, а не смысл: верный вывод с верными полями засчитывается, даже если агент «угадал» его без анализа. Защита от угадывания — в требовании полного набора доказательств из существующих ID и в штрафе FP.
* Доказательства должны **содержать** один из эталонных наборов; лишние существующие ID (до 10) не штрафуются. Это сознательный компромисс: агент не обязан знать минимальный набор.
* Допуск 1 минимальная единица одинаков для всех типов, хотя для `duplicate_invoice`, `payment_allocation` и `period_cutoff` суммы точные. Выгоды это не даёт: соседняя сумма не является другим ответом.
* Награда не доказывает пригодность агента для реального аудита.

## История версий

* **1.1.0** — валидатор мягче к отдельным выводам: корректный код валюты не из эпизода → FP вместо −1 за весь ответ; неизвестные ключи внутри вывода игнорируются (верхний уровень строгий); ID без префикса разрешается в канонический, если существует ровно в одной публичной таблице. Oracle, молчание, flag-all, дубли, инвариантность к перестановке и смене ID — без изменений.
* **1.0.0** — первая версия.
