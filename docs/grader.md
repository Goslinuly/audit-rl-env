# Оценщик (`auditgym.grader`)

Владелец: участник 3. Контракт для среды (участник 2), runner и политик (участник 4) и жюри: как устроены валидация, нормализация, сопоставление и награда. Всё ниже — открытый код, правила не меняются без смены `GRADER_VERSION`.

## Быстрый старт

```python
from auditgym.grader import Grader
res = Grader().score(findings, truth=truth, public=public, inspection_steps=12)  # так вызывает среда
res = Grader().score(findings, "episodes/dev/dev_03", inspection_steps=12)       # прямо с диска
res.reward, res.precision, res.recall, res.f1, res.tp, res.fp, res.fn
res.matches          # [{finding_index, issue_id, amount_diff}]
res.finding_reasons  # по каждому выводу: "tp" или причина отказа (см. ниже)
res.missed_issue_ids, res.by_type, res.errors, res.valid, res.grader_version
```

```bash
python -m auditgym.grader score --episode episodes/dev/dev_07 --findings answer.json --steps 20
python -m auditgym.grader selfcheck            # oracle = 1, молчание, flag-all < 0, перестановка, смена ID на всех эпизодах
```

Среда подхватывает оценщик автоматически (`auditgym.env.grading.default_grader`): заглушка `StubGrader` больше не используется. Агент получает только `reward` и только в режиме `train`; всё остальное уходит в `env.grade_log` (для runner и разбора сбоев).

Оценщик — чистая функция: без случайности, часов и глобального состояния, входные данные не изменяет (проверяется тестом R20). Арифметика награды точная (`Fraction`), в `float` переводится один раз — одинаковые входы дают побитово одинаковую награду.

## 1. Валидация `findings.json` (`validate.py`)

Любое нарушение структуры → вся отправка недействительна, `reward = −1`, `valid = false`, текст ошибок — в `errors` (в журнал оценщика, не агенту).

Структурная ошибка — только неверный тип значения, отсутствующее обязательное поле или превышенный лимит. Всё остальное (неизвестный тип ошибки, валюта, ID, пустой `affected_ids`, огромная сумма) — обычный вывод, который не сопоставится и станет одним FP.

| Поле | Правило |
| --- | --- |
| верхний уровень | объект: `episode_id` (строка, равна id эпизода), `findings` (список), необязательный `schema_version`; другие ключи игнорируются |
| `findings` | не больше **30** |
| вывод | объект с полями ниже; `explanation` необязателен; неизвестные ключи игнорируются |
| `type`, `currency` | строки |
| `affected_ids` | список строк |
| `evidence_ids` | список строк, не больше **10** до удаления повторов |
| `claimed_amount_minor` | целое; `bool` и любой `float` (даже `100.0`) отвергаются |
| `explanation` | строка не длиннее **1000** code points; оценщик её не читает |

Схема — `schemas/findings.schema.json`; тест проверяет, что схема и валидатор принимают и отвергают одно и то же. Единственное различие: JSON Schema 2020-12 считает `100.0` целым, валидатор — нет.

## 2. Нормализация (`normalize.py`)

ID и валюта сравниваются точно: с учётом регистра и пробелов, без удаления или добавления префиксов, алиасов и поиска похожих. Списки ID превращаются в множества — порядок и повторы внутри списка не важны. Канонические ID: `ledger:<row_id>`, `invoices:<invoice_id>`, `payments:<payment_id>`, `fx:<date>/<src>/<tgt>`.

ID, которого нет в публичных записях эпизода, — «неизвестный»; вывод с хотя бы одним неизвестным ID (в affected или evidence) не может быть TP. Перевод ID без префикса делает только адаптер жюри, до оценщика (`docs/judge.md`).

## 3. Сопоставление (`matcher.py`)

Пара (вывод, issue) **совместима**, если по порядку:

| # | Проверка | Причина при отказе |
| --- | --- | --- |
| 1 | все ID вывода существуют в публичных записях | `unknown_id` |
| 2 | тот же `type` | `type` |
| 3 | множество `affected_ids` = каноническим `affected_ids` issue | `affected_ids` |
| 4 | та же валюта | `currency` |
| 5 | \|claimed − expected\| ≤ `tolerance_minor` ошибки | `amount` |
| 6 | хотя бы один `evidence_set` issue ⊆ `evidence_ids` | `evidence` |

**Допуск** публикуется заранее по типам (`TOLERANCE_BY_TYPE`): `fx_conversion` — 1 минимальная единица (policy округляет каждую строку), остальные — 0. Генератор пишет это число в `truth.json` (`tolerance_minor`), matcher берёт его оттуда; если поля нет, допуск 0.

**Паросочетание.** На двудольном графе совместимых пар берётся **максимальное** паросочетание, а среди всех максимальных — с лексикографически наименьшей отсортированной последовательностью пар `(issue_id, индекс вывода)`. Tie-break решает только *какой* вывод получит зачёт, но не *сколько*. Тест сверяет выбор с полным перебором.

Вне паросочетания: каждый вывод — **FP** (включая точные повторы засчитанного вывода — причина `duplicate`), каждый issue — **FN**. В `finding_reasons` для FP указана первая не пройденная проверка относительно «ближайшего» issue (того, где пройдено больше проверок).

## 4. Метрики и награда (`reward.py`)

```
P  = TP / (TP + FP)            0 при нулевом знаменателе
R  = TP / (TP + FN)            0 при нулевом знаменателе
F1 = 2TP / (2TP + FP + FN)     пустой эталон и пустой ответ → 1; пустой эталон и есть выводы → 0
reward = clip(2·F1 − 1 − 0.002·inspection_steps, −1, 1)
```

`inspection_steps` — число шагов до `submit`, без самого `submit` (при обрыве по лимиту — все сделанные шаги; ответ при обрыве = `findings: []`). Экспериментальной награды нет: в результате одна общая `reward`.

Справочные значения:

| Ситуация | reward |
| --- | --- |
| полный верный ответ, 0 шагов | 1.0 |
| полный верный ответ за 10 / 90 шагов | 0.98 / 0.82 (разница ровно 0.16) |
| молчание на книге с ошибками | −1.0 |
| молчание на чистой компании, 0 / 100 шагов | 1.0 / 0.8 |
| любое обвинение на чистой компании | −1.0 |
| неверная структура | −1.0 |

| `test_grader_strict.py` | правила 2.0.0: точное сравнение ID и валюты; неверное содержание вывода = один FP; лишние ключи игнорируются |
| `test_grader_schemas.py` | все 10 схем валидны; все 21 эпизод и все пресеты им соответствуют; схема findings ≡ валидатор на 300+ ответах; trajectory_line запрещает ключи эталона |

| # | Проверка | Ожидание |
| --- | --- | --- |
| R01 | полный ответ vs молчание на книгах с ошибками | +1 / −1 |
| R02 | молчание vs ложное обвинение на чистых | +1 / −1 |
| R03 | верный вывод ×2 / ×30, весь ответ ×2 | дубли = FP, награда строго ниже |
| R04 | «пометить всё» (30 выводов) | F1 < 0.4, награда < 0 на каждом эпизоде |
| R05 | один ответ за 10 и 90 шагов | разница 0.16; полный ответ за 99 шагов > молчания и flag-all |
| R06 | выдуманные ID, мусор в evidence, выдуманный ID без префикса, пути к файлам | FP |
| R07 | верные affected_ids, неполные доказательства | FP (`evidence`) |
| R08 | верная сумма в другой валюте или в другом написании валюты; сумма вне допуска типа | FP; в пределах допуска — TP |
| R09 | длинное «убедительное» explanation, prompt-injection в тексте | на награду не влияет |
| R10 | неверная структура (типы, обязательные поля) | −1 |
| R11 | 31 вывод, 11 доказательств, 1001 символ, float | −1; ровно на лимитах — валидно |
| R12 | повторный submit | награда и журнал не меняются |
| R13 | тайм-аут 60 с и 100 шагов | truncated, оценка как пустой ответ |
| R14 | часть цепочки сценария A | молчание < частичный < полный |
| R15 | перестановки выводов | та же награда, TP, FP, FN |
| R16 | неверный тип; надмножество/подмножество affected; дубль указан на оригинал | FP |
| R17 | 2000 случайных ответов (фаззинг) | награда ∈ [−1, 1], ≤ oracle, детерминирована |
| R18 | граф, где жадное сопоставление ошибается; tie-break | максимальное паросочетание; наименьшая последовательность пар |
| R19 | смена ID + перестановка строк | oracle = 1.0; награда любых ответов сохраняется после переименования |
| R20 | режим `eval`; неизменность входов | агенту 0, оценка только в `grade_log`; оценщик ничего не пишет |

Мутационная проверка самих тестов: каждая из подмен — широкий допуск, отключение проверки доказательств / валюты / неизвестных ID, «подмножество affected достаточно», дедупликация повторов, F1 = 1 на чистых при FP, приём float, снятие лимита 30, жадное сопоставление вместо максимального — роняет от 1 до 18 тестов.

## Ограничения

* Оценщик проверяет поля и доказательства, а не смысл: верный вывод с верными полями засчитывается, даже если агент «угадал» его без анализа. Защита от угадывания — в требовании полного набора доказательств из существующих ID и в штрафе FP.
* Доказательства должны **содержать** один из эталонных наборов; лишние существующие ID (до 10) не штрафуются. Это сознательный компромисс: агент не обязан знать минимальный набор.
* Допуск 1 для `fx_conversion` засчитывает соседнюю сумму; точный расчёт по policy его не требует.
* Награда не доказывает пригодность агента для реального аудита.

## История версий

* **2.0.0** — по определениям проверок жюри: точное сравнение ID и валюты (отменены обрезка, регистр, алиасы и ID без префикса), допуск по типам из `truth.json`, неверное содержание вывода — FP вместо −1, лексикографический tie-break.
* **1.1.0** — валидатор мягче к отдельным выводам: корректный код валюты не из эпизода → FP вместо −1 за весь ответ; неизвестные ключи внутри вывода игнорируются (верхний уровень строгий); ID без префикса разрешается в канонический, если существует ровно в одной публичной таблице. Oracle, молчание, flag-all, дубли, инвариантность к перестановке и смене ID — без изменений.
* **1.0.0** — первая версия.
