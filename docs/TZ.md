# ТЗ: RL-среда для ИИ-аудитора (FinTech хакатон)

Команда: 4 человека · Онлайн-этап: 19–22 ноября 2026 · Сдача: 22.11.2026, 23:59 (Астана)

## Цель и рамки

Строим воспроизводимую RL-среду `auditgym`: генератор синтетических компаний со скрытыми ошибками, Gym-подобный контракт `reset/step`, инструменты расследования и оценщик с наградой. Модель мы не обучаем — жюри оценивает корректность среды и оценщика, а не награду нашего агента.

**Жёсткие ограничения (нарушение = блокировка оценивания):**

- Python 3.11, 2 CPU, 4 ГБ RAM, без GPU, без сети, без платных API; 60 с и 100 шагов на эпизод, ≤ 1 ГБ на решение.
- Агент никогда не видит `truth.json`, `provenance.json` и seed — ни в наблюдениях, ни в путях, ни в текстах ошибок, ни в `info`.
- Деньги — целые минимальные единицы (`*_minor`), FX-курсы — десятичные строки, время — ISO-8601 со смещением. Никаких float в деньгах.
- Только вымышленные данные. Никаких реальных компаний, карт, персональных данных.
- Одинаковые seed + config + версия + действия → байт-в-байт одинаковые записи, переходы и награды.

**Как нас оценят (100 баллов):**

| Блок | Баллы | Кто отвечает |
| --- | --- | --- |
| Контракт и изоляция (20 проверок reset/step, схем, лимитов, утечек) | 25 | Участник 2 |
| Данные и эталон (20 закрытых эпизодов: бухгалтерские равенства, расхождение, достаточность доказательств) | 25 | Участник 1 |
| Надёжность награды (20 проверок matcher, FP, дублей, атак) | 25 | Участник 3 |
| Воспроизводимость и обобщение (повтор seed, перестановка и смена ID) | 15 | Участники 1 + 2 |
| Инженерия и объяснение (одна команда, версии, траектории, разбор сбоев, ограничения) | 10 | Участник 4 |

Не тратим время на UI и обучение весов — баллов они не дают. Порядок работы: контракт + 2 типа ошибок → все 4 типа + чистые случаи → сочетания, изоляция, атаки.

## Архитектура и общие контракты

Четыре модуля с чёткими границами, по одному на человека. Генератор пишет эпизод в две папки — `public/` (видит среда) и `private/` (видит только оценщик). Среда отдаёт агенту только запрошенные строки из `public/`; на `submit` вызывает оценщика, который читает `private/` в отдельном процессе/объекте.

| Путь | Что там | Владелец |
| --- | --- | --- |
| `auditgym/generator/` | скрытая история компании, документы, инъекция ошибок, отвлекающие случаи | 1 |
| `auditgym/env/` | `AuditEnv.reset/step`, инструменты, калькулятор, пагинация | 2 |
| `auditgym/grader/` | валидация findings, matcher, метрики, награда | 3 |
| `auditgym/policies/`, `auditgym/runner/` | 4 базовые политики, запуск эпизодов, запись траекторий, отчёт | 4 |
| `schemas/` | JSON Schema: config, manifest, findings, truth, действия, наблюдения | 3 (согласуют все) |
| `configs/train/`, `configs/dev/` | версионированные конфиги и списки seed | 1 |
| `episodes/train/`, `episodes/dev/` | 10 + 10 сгенерированных эпизодов | 1 |
| `tests/` | тесты по модулям + `tests/acceptance/` (имитация проверок жюри) | все, сборка — 4 |
| `Dockerfile`, `Makefile`, `README.md`, `DESIGN.md` | контейнер, `make check`, документация | 4 |

**Контракты фиксируем в первый вечер (19.11), дальше меняем только через PR с апрувом всех:**

1. `generate(seed: int, config: dict) -> Episode` — чистая функция, единственный источник случайности — `random.Random(seed)`. `Episode.public` = manifest, ledger, invoices, payments, fx, policy; `Episode.private` = truth, provenance.
2. Формат файлов — строго по разделу 03 условий (`ledger.csv`, `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json`, `manifest.json`). Отсутствующая ссылка = `null`.
3. ID для доказательств и affected_ids: единая форма `"<table>:<id>"`, например `ledger:L0042`, `invoices:INV-7Q2K`, `payments:PAY-19XA`, `fx:2026-03-31/USD/KZT`.
4. Канонические `affected_ids` по типу ошибки (таблица у участника 1) — одно правило, записанное в `DESIGN.md` и в `grader/normalize.py`.
5. `AuditEnv(mode: "train"|"eval").reset(seed, config) -> (obs, info)`, `.step(action) -> (obs, reward, terminated, truncated, info)`; всё JSON-сериализуемо.
6. `Grader.score(findings: dict, episode_dir) -> GradeResult(reward, precision, recall, f1, tp, fp, fn, matches, errors)` — живёт вне объекта среды; агент получает только `reward` и только в режиме train.
7. `Policy.act(obs) -> action`; только `OraclePolicy` получает truth через конструктор из runner, никогда через среду.

**Правила работы:** ветка на задачу, PR в `main`, CI (`make check`) зелёный перед мерджем, зависимости — только зафиксированные в `pyproject.toml`. Минимум зависимостей: stdlib + `jsonschema` + `pytest`.

## Участник 1 — Генератор компаний и эталон (`auditgym/generator/`)

Задача: по seed и config детерминированно строить согласованную историю компании, из неё — документы, затем вносить ошибки с записанным причинным изменением.

**Конвейер (строго в этом порядке):**

1. `history.py` — скрытая история: компания, базовая валюта, часовой пояс, контрагенты (вымышленные имена из слогов), сделки → счета → платежи → курсы. Все суммы — int minor units, курсы — `Decimal`.
2. `render.py` — из истории строятся `ledger.csv` (двойная запись: каждая операция — сбалансированные debit/credit), `invoices.jsonl`, `payments.jsonl`, `fx.csv`, `policy.json`, `manifest.json`.
3. `invariants.py` — проверка чистой истории: Дт = Кт по каждой операции и в целом; сумма строк счёта = total; распределение платежей сходится; конверсия = курс из `fx.csv` по правилу `policy.json` + округление; все проводки в периоде.
4. `errors/*.py` — инъекторы ошибок. Каждый меняет конкретные записи, пишет дифф в `provenance.json` (до/после) и эталонный issue в `truth.json`.
5. `distractors.py` — корректные подозрительные случаи (не попадают в truth).
6. `verify.py` — независимая проверка: после инъекции каждое объявленное расхождение действительно видно в публичных записях, и каждый набор доказательств состоит из существующих публичных ID и достаточен, чтобы пересчитать `expected_amount_minor`. Упала проверка — эпизод не выпускается.
7. `transforms.py` — безвредные преобразования для парных проверок: перестановка строк и переименование ID с согласованным переписыванием truth (`remap_ids`, `shuffle_rows`).

**Типы ошибок и канонический эталон (каждый включается и настраивается независимо в config):**

| type | Что ломаем | affected_ids | expected_amount_minor | Допустимые доказательства |
| --- | --- | --- | --- | --- |
| `duplicate_invoice` | вторая копия счёта с новым invoice_id и теми же entity/строками/суммой, проведена в леджер | дубль (более поздний по `issued_at`, при равенстве — больший doc_id) | total дубля, валюта счёта | {оригинал, дубль} или {оригинал, строка леджера дубля} |
| `payment_allocation` | платёж не распределён (`invoice_refs` пуст) или распределён частично | платёж + счёт | нераспределённый остаток, валюта платежа | {платёж, счёт, строка леджера платежа} |
| `fx_conversion` | взят курс другой даты (вопреки policy) или неверный курс | строки леджера с конверсией | разница в базовой валюте (модуль) | {строка леджера, документ-источник, строка fx правильной даты} |
| `period_cutoff` | операция из соседнего периода проведена в текущем (или наоборот), часто из-за часового пояса | строки леджера | сумма проводки в базовой валюте | {строка леджера, документ с реальной датой} |

Точные правила согласуй с участником 3 в первый вечер и запиши в `DESIGN.md`. Эталон описывает реальное расхождение, а не «подозрительную строку», и не требует фактов, которых нет в публичных записях.

**Взаимодействующие сценарии (минимум 2):**

- **A.** Частичный платёж в иностранной валюте на границе периода: платёж 23:30 по UTC+5 последнего дня периода (уже следующий период в часовом поясе компании или наоборот), распределён частично и конвертирован по курсу другой даты → 2–3 связанных issue, каждый с отдельно проверяемой суммой.
- **B.** Дубль счёта в USD, дубль оплачен и проведён с неверной датой курса.
- В provenance видно, какие изменения к какому issue относятся; сумма каждого issue считается после применения остальных (порядок фиксирован и задокументирован).

**Отвлекающие корректные случаи:** разбитая оплата одного счёта 2–3 платежами; возвраты; ежемесячные подписки с одинаковой суммой и разными периодами услуг; операции за минуту до границы периода; курс за предыдущий рабочий день в выходные, если так сказано в policy.

**Config (`configs/*.json`, поле `config_version`):** `n_ledger_rows` (200–2000), `n_documents` (20–200), `error_counts` по типам (0–12 суммарно), `interactions: [A, B]`, `distractor_rate`, `currencies`, `timezone`, `clean: bool`. Варьируем имена, ID, порядок, суммы, валюты (KZT, USD, EUR, JPY с разной разрядностью), часовые пояса. ID не должны кодировать ошибку (никаких `INV-DUP-...`, никаких последних номеров у внесённых записей) — ID генерируются и перемешиваются после инъекции.

## Участник 2 — Среда, инструменты и изоляция (`auditgym/env/`)

Задача: Gym-подобный контракт `reset/step` с узким набором инструментов и нулевой утечкой эталона. Утечка блокирует оценку всей команды.

**API:**

- `AuditEnv(mode="train"|"eval", grader=None, max_steps=100, time_limit_s=60)`; можно унаследовать `gymnasium.Env`, но интерфейс должен работать и без него.
- `reset(seed, config) -> (obs, info)`: вызывает генератор (или загружает готовый эпизод), полностью пересоздаёт состояние. Первое наблюдение: `task`, `manifest`, краткая `policy`, `steps_remaining=100`, список доступных действий. В `info` — только `episode_id`, `env_version`, `config_version`. Никакого seed в наблюдении.
- `step(action) -> (obs, reward, terminated, truncated, info)`: action — JSON `{"name": ..., "args": {...}}`.

**Действия:**

| Действие | Поведение |
| --- | --- |
| `list_records(table, cursor, limit)` | table ∈ {ledger, invoices, payments, fx}; limit ≤ 50; курсор — непрозрачная строка, стабильная в рамках эпизода |
| `get_record(table, id)` | одна запись или ошибка `not_found` |
| `get_document(doc_id)` | полный документ (счёт с line_items или платёж) |
| `calculator(expression)` | только числа, `+ - * / ( )`, десятичные; свой парсер на `Decimal`, **не** `eval`; лимит длины и глубины, деление на 0 → ошибка |
| `submit(findings)` | валидация схемы → оценщик → `terminated=true` |

**Правила шага:**

- Каждое действие, включая ошибочное и `submit`, расходует 1 шаг. Максимум 100.
- Неизвестное действие / ID / неверные аргументы → `{"error": {"code": "not_found"|"bad_args"|"unknown_action", "message": ≤ 200 символов}}`. Текст ошибки не подсказывает, какие ID существуют, без stack trace и путей.
- Награда за исследование = 0. В `train` после `submit` reward = терминальная награда; в `eval` reward = 0, результат уходит только в журнал оценщика.
- Лимит шагов или 60 с → `truncated=true`, итоговый ответ пустой (оценивается как `findings: []`). Шаг после завершения → ошибка без изменения состояния; повторный `submit` не пересчитывает награду.
- Размер одного action ограничен (например, 64 КБ).

**Изоляция:**

- Среда держит в памяти только `public` часть эпизода. `private` живёт в объекте оценщика, а в режиме `eval` — в отдельном процессе; среда передаёт туда только findings.
- Данные возвращаются копиями, агент не может изменить записи.
- В наблюдениях нет полей provenance, путей к файлам, seed, типов внесённых ошибок.
- Нет shell, SQL, доступа к файлам и сети через действия.

JSON Schema для действий и наблюдений — `schemas/action.schema.json`, `schemas/observation.schema.json`.

## Участник 3 — Matcher, награда и схемы (`auditgym/grader/`, `schemas/`)

Задача: открытый, детерминированный и устойчивый к атакам оценщик. Схемы пишешь первым в день 1 — от них зависят все.

**Схемы (день 1, до 18:00):** `config`, `manifest`, `policy`, `findings`, `truth`, `provenance`, `action`, `observation`, `trajectory_line`. Везде `schema_version`.

**Валидация findings (`validate.py`):** `episode_id` совпадает; ≤ 30 выводов; ≤ 10 `evidence_ids`; `explanation` ≤ 1000 символов; `type` из списка; `claimed_amount_minor` — int; `currency` — ISO-4217 из manifest. Любое нарушение → reward = -1, ошибка в журнал оценщика (не агенту в eval).

**Нормализация (`normalize.py`, опубликовать и задокументировать):** trim, единый регистр префикса таблицы, дедупликация и сортировка ID, валюта в верхний регистр. Никакого «угадывания» — несуществующий ID не сопоставляется.

**Сопоставление (`matcher.py`):**

1. Пара (finding, truth issue) совместима, если: тот же `type`; нормализованные `affected_ids` = каноническим; `currency` совпадает; `|claimed - expected| ≤ tolerance` (предлагаемый допуск: `max(1, единица округления из policy)` минимальных единиц — константа в коде и в DESIGN.md); хотя бы один допустимый набор доказательств ⊆ `evidence_ids`.
2. На двудольном графе совместимых пар — максимальное паросочетание (Хопкрофт–Карп или перебор — выводов ≤ 30). Детерминированный tie-break: меньшая разница сумм, затем порядок вывода в списке, затем issue_id. Правило опубликовать.
3. Несопоставленные и повторные выводы → FP; несопоставленные issue → FN.

**Метрики и награда (`reward.py`):** P = TP/(TP+FP), R = TP/(TP+FN), F1 = 2TP/(2TP+FP+FN); нулевой знаменатель → 0; пустой эталон + пустые выводы → F1 = 1; пустой эталон + есть выводы → F1 = 0.

```
reward = clip(2 * F1 - 1 - 0.002 * inspection_steps, -1, 1)
```

`inspection_steps` = число шагов до submit (без самого submit) — зафиксировать в DESIGN.md. Экспериментальная награда — только отдельным полем, общая остаётся основной. Награда не смотрит на текст `explanation`.

**Атакующие тесты (`tests/grader/`) — каждый с числовой проверкой:**

| Тест | Ожидание |
| --- | --- |
| полный верный ответ vs молчание на книге с ошибками | верный ≈ +1, молчание = -1 |
| молчание vs ложное обвинение на чистой компании | молчание ≈ +1, обвинение = -1 |
| верный вывод × 2 / × 30 | дубли = FP, награда ниже, чем у одного |
| «пометить всё»: все строки × все типы (до 30) | F1 низкий, награда < 0 |
| те же верные ответы за 10 и за 90 шагов | разница ровно 0.16, порядок не меняется |
| угаданные / несуществующие ID | FP |
| верные affected_ids, но доказательства неполные | FP |
| верная сумма в другой валюте / сумма вне допуска | FP |
| длинное убедительное explanation без полей | не влияет |
| неверная структура, 31 вывод, 11 доказательств, float в сумме | -1 |
| повторный submit, тайм-аут | награда не меняется / пустой ответ |
| частично верный ответ на сценарии A | награда между молчанием и полным ответом |
| перестановка выводов в списке | награда та же |

Плюс property-based тест (`hypothesis`, если добавим в зависимости): для случайных findings награда всегда в [-1, 1] и никогда не превышает награду oracle.

## Участник 4 — Политики, траектории, оценка, инфраструктура (`auditgym/policies/`, `auditgym/runner/`, Docker, docs)

Задача: всё, что превращает код в сдаваемый продукт: четыре базовые политики, запись траекторий, единая команда проверки, контейнер, документация и демо.

**Базовые политики (`act(obs) -> action`):**

| Политика | Поведение | Ожидаемая награда |
| --- | --- | --- |
| `RandomExplorer(seed)` | случайные list/get, затем случайный или пустой submit | около -1 на битых, случайно на чистых |
| `Reconciler` | читает таблицы страницами, ищет дубли по (entity, total, line_items), несходящиеся платежи, пересчитывает FX по policy, проверяет границы периода; укладывается в 100 шагов | промежуточная; важно честно измерить, а не задрать |
| `FlagAll` | максимум 30 выводов по всем типам и видимым строкам | < 0 |
| `Oracle(truth)` | сразу submit верных выводов с первым допустимым набором доказательств; truth передаёт runner, не среда | 1.0 на каждом эпизоде |

**Runner (`python -m auditgym.runner`):** прогоняет политики по списку эпизодов/seed, пишет `trajectories.jsonl` (`episode_id, step, action, observation, reward, terminated, truncated` + `policy`, `env_version`) и `results.csv` с P, R, F1, возвратом, шагами, временем. После записи — автоматический leak-scan траекторий.

**Приёмочный набор (`tests/acceptance/`) — имитация жюри:** 20 своих «скрытых» эпизодов (5 чистых, 5 со сценариями A/B, 10 смешанных) × 4 политики + 20 парных проверок (повтор seed → идентичные траектории; перестановка и смена ID → oracle снова 1.0). Итог — таблица «пройдено X/20» по каждому критерию жюри.
